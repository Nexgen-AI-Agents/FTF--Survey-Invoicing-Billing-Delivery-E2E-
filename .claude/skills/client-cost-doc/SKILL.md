# Client Requirements, Development & Cost document set

Produce three deliverables in `<OUTPUT>/<version>/`, all generated by ONE re-runnable Python
script so re-running always reflects current state:
1. Word (`.docx`)
2. PDF (render a self-contained HTML via headless Chrome/Edge if no PDF engine exists)
3. Excel (`.xlsx`)

Cover: executive summary + at-a-glance stats, system/architecture overview, engineering
principles, capabilities (delivered / in progress / planned), defects (fixed / open), release
history, and a cost section. Use libraries already present (`python-docx`, `openpyxl`, `reportlab`).

## Step 0 — gather inputs (ask only if not obvious)
- **PROJECT NAME**
- **REPO PATH** (absolute)
- **PRODUCTION API KEY name(s)** — the Anthropic key(s) this project's live app uses (or "none /
  not an AI app", in which case skip the cost section entirely)
- **OUTPUT FOLDER** (default `documents/resources/client`; create a versioned subfolder `vX.Y`)

## Step 1 — content (requirements / bugs / deployments)
- If the repo has tracker files (e.g. `project_management/{REQUIREMENTS,BUGS,DEPLOYMENTS}.md`),
  parse ALL of them with a generic markdown-table parser. Do NOT stop at the first table
  (multiple sections/headers are common) and do NOT silently truncate.
- Reconcile against git: count distinct version tags in commit subjects and total commits. If the
  trackers under-record what git shows, SAY SO — never invent rows or claim an unsupported number.
- If there are no trackers, derive lists from git history (tags, commit subjects, CHANGELOG).
- After generating, verify the output row counts equal the source counts (no drops).

## Step 2 — cost (only if it's an AI app with an Anthropic key)
Report TWO separate, clearly-labeled numbers, both MEASURED — never estimated. The bundled
scripts in `scripts/` implement this; edit their small CONFIG block per project.

**PRODUCTION (runtime — what users cost), authoritative — `scripts/fetch_production_cost.py`:**
- Read the Admin key from `.env` (never print/hardcode it).
- Pull the Admin Usage API (`/v1/organizations/usage_report/messages`) FILTERED BY `api_key_id`
  to THIS project's production key(s). The Cost API CANNOT filter by key (only workspace/
  description), and a key often shares a workspace with unrelated projects — so isolate by
  `api_key_id` and price tokens at official list rates.
- VALIDATE: pull the Cost API for that key's whole workspace and confirm your priced total
  reproduces it. **GOTCHA: the Cost API `amount` is in CENTS — divide by 100.** When your priced
  workspace total == Cost-API/100, your pricing is correct to the cent.
- **GOTCHA: usage `cache_creation` is NESTED** — read `cache_creation.ephemeral_5m_input_tokens`
  and `ephemeral_1h_input_tokens` (the flat field is 0). Pricing per 1M: input full; cache_read
  ≈ 0.1×; cache_write_5m ≈ 1.25×; cache_write_1h ≈ 2×; output at the model's output rate.

**DEVELOPMENT (build cost in Claude Code), measured — `scripts/verify_dev_cost.py`:**
- Read this project's Claude Code transcripts at `~/.claude/projects/<slug>/*.jsonl`, where
  `<slug> = re.sub(r'[^A-Za-z0-9]', '-', REPO_PATH)`. Sum each assistant message's `usage`.
- **CRITICAL: DEDUPE by API message id (`message.id`).** Claude Code re-logs resumed/compacted
  sessions, so a raw sum double-counts ~5×. Price at list rates.
- SCOPE STRICTLY to this project's transcript folder(s). Claude Code keys are shared across many
  projects — never attribute another project's work here. List sibling/related working copies
  separately; include only if truly this project.
- VALIDATE (`scripts/validate_dev.py`): sum deduped tokens across ALL local projects (window-
  filtered) and compare to the Admin API total for the Claude Code keys; reconcile within
  ~10–15% (residual gap = same-day reporting lag). State the validation result in the doc.
- The dev dollar is the list-rate VALUE of measured tokens (±~10%), not cent-exact like
  production — say so plainly.

## Accuracy & honesty rules (non-negotiable)
- Every number comes from a real source (Admin API, git, trackers) — never fabricate or guess.
- Scope everything to THIS project only; never mix in another project's tokens, cost, or rows.
- If a figure looks implausible, investigate before publishing (a value exceeding the whole org's
  spend means double-counting or a unit error — both happened on the first build of this skill).

## Style — simple & self-explanatory
- A non-technical reader must understand it with no glossary. Plain language, short notes.
- Lead with the answer (a TOTAL, then the parts). One clear cost table — not a methodology wall.
- Once you have measured numbers, DELETE any estimate/reconstruction scaffolding — it only confuses.
- No dead columns, no internal jargon, no half-data.

## Process
- Put data-pulling in small, separate, re-runnable scripts; read secrets from `.env` only.
- QA: extract the PDF text and xlsx cells; verify key figures and row counts are present/correct;
  fix and re-verify.
- Render HTML→PDF headless, e.g. (Windows Edge):
  `msedge --headless --disable-gpu --no-pdf-header-footer --print-to-pdf="out.pdf" "file:///abs.html"`
  (macOS/Linux: use `google-chrome`/`chromium` with the same flags).
- Git: do NOT commit secrets (`.env`, `*.ppk`, keys) or runtime PII. Commit the OUTPUT folder
  (force-add if gitignored) on a branch and push — only if the user asks.
- Final summary: state where each number came from and its confidence level.

## Bundled helper scripts (templates — edit the CONFIG block at the top of each)
- `scripts/fetch_production_cost.py` — production cost, key-id scoped, validated vs Cost API.
- `scripts/verify_dev_cost.py` — development cost from this repo's transcripts, deduped.
- `scripts/validate_dev.py` — cross-check transcripts vs Admin API (sanity/confidence).
